- [x] **Redact enrolled children's names from AI prompts (free text)** — `generate`, `personalise`, `follow-up-activity`, and `group-activity` already withheld structured identity fields (`first_name`, DOB, `child_id`) from the Anthropic prompt, but the *free-text* fields (observation notes, interests, additional needs — whether pulled from the DB or typed fresh by an educator) routinely contain the child's actual first name written in prose ("Emma loved the sensory bin today") and were sent to Claude unredacted. `childNameGuard.ts` gained `redactEnrolledChildNames()` (reuses the existing per-service enrolled-name lookup from the document-review guard, but substitutes "the child" instead of blocking the request — blocking isn't viable here since observations are inherently about one child). Wired into all four generation routes. (commit pending) **Scope note:** regex match on `children.first_name` only, same precedent as the existing document-review guard — not general PII detection (won't catch nicknames, last names, or a name typed with unusual spelling).
- [x] **Encrypt-at-rest for medical/compliance fields** — `children.additional_needs`, `child_health_plans.*` (triggers/signs_and_symptoms/emergency_steps/emergency_medication), and `staff_compliance.reference_number` (WWCC etc.) were plaintext in Supabase, protected only by RLS — same as every other table in the app (confirmed: no `centres`/`organisations` sensitive fields — WWCC, invoices — have any encryption either). New `lib/encryption.ts` does application-layer AES-256-GCM, key held only in server env (`FIELD_ENCRYPTION_KEY`), never in Supabase — a leaked service-role key or raw DB dump alone can no longer read these fields, both the key AND DB access are required. Deliberately **not** a schema migration or destructive backfill: existing plaintext rows are recognised and passed through unchanged (no `enc:v1:` prefix = legacy plaintext), so there's no risky bulk rewrite of live medical records — a row gets encrypted the next time it's saved. Both directions fail open by design (encrypt skips silently to plaintext if the key's unset; decrypt returns the raw stored value if the key's wrong or missing) specifically because a misconfiguration must never make an anaphylaxis emergency plan unreadable or block a save. Wired into every read/write path for these columns (`children.ts`, `digest.ts`, `signinBoard.ts` — feeds the live onsite board, `healthPlans.ts`, the health-plan edit page, the excursions page, `compliance/page.tsx`, and all the corresponding server actions), verified via full-repo grep that nothing selects these columns without decrypting. (commit pending) **MANUAL STEP:** set `FIELD_ENCRYPTION_KEY` in Vercel env to the exact value in local `.env.local` (same Supabase DB is shared between local dev and prod, so the key must match or one environment can't read what the other encrypted) — until this is set in Vercel, production keeps saving these fields as plaintext exactly as it does today (safe, just not yet protected).

## Image generation (Pollinations) — outage resolved 2026-08-18, watch for recurrence
- **2026-08-05:** Pollinations.ai (the free, keyless image API `/api/generate-image` relies on for every printable sheet's picture) started returning HTTP 402 "Insufficient balance" for every model. Every picture-having sheet (activity sheet, drawing frame, card set, name colouring) couldn't produce a real picture.
- **2026-08-18:** Retested the exact endpoint the route calls with a fresh, uncached prompt (`CF-Cache-Status: DYNAMIC`, real image returned) — it's generating again, no code change needed. Free tier appears restored on Pollinations' end. Deliberately not paying for a fallback provider while pre-revenue and this now costs nothing — revisit only if it outages again. If it recurs, cheapest options to compare before paying for anything: Cloudflare Workers AI (free daily allowance) or Google Gemini/Imagen free tier.
- **Fixed while investigating (commit pending):** two real app bugs, independent of the outage above —
  (a) `name_colouring` sheets never had an image option at all; wired to the same `image_subject` field the AI already sets for other templates (only when the educator's request implies a theme — plain name sheets stay text-only).
  (b) Every picture-having sheet silently showed a permanent blank box on ANY image failure (not just this outage) — the small preview thumbnail's error handler called `setImageUrl(null)`, wiping the shared image state out from under the full-size picture before it could show its own error. Now each shows its own "Image couldn't be generated" message instead.
  Verified with Playwright (`playwright/tests/name-colouring-image.spec.ts`) — with the real outage still in effect, the sheet now shows the clear error message instead of hanging in "Generating…" or going blank.
