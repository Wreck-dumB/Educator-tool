## Recently fixed
- [x] **Permission Slips: infinite RLS recursion blocked every send** — `permission_slips` and `permission_slip_targets` (migration 0013) had circular RLS policies, each doing a raw `EXISTS` subquery against the other; Postgres has to re-evaluate each table's own policies while resolving a cross-table subquery, so A needed B evaluated, which needed A evaluated again. 100% reproducible (`42P17 infinite recursion detected in policy`) on every real send — found during the 2026-08-18 QA pass. Migration 0063 moves the cross-table reads into two `SECURITY DEFINER` helpers (`permission_slip_owner`, `permission_slip_sent_to_linked_child`), same established pattern as `has_service_role()`/`is_linked_parent()` elsewhere in this schema — a security-definer function's internal queries aren't subject to the caller's RLS re-evaluation of the *other* table, so neither policy re-enters the other's stack. Also closed a related, previously-latent gap surfaced while tracing this: `permission_slip_targets`/`_versions`/`_signatures` were still gated on the pre-0020 `educator_user_id = auth.uid()` check, which only the Director's own uid ever satisfies — 0020 widened `permission_slips` itself to let 2IC+ create slips on the service's behalf, but never updated these sibling tables, so a 2IC could pass the parent slip's INSERT check yet be blocked from inserting its version/targets rows. Rewritten to `has_service_role()` to match 0020's intended model. Applied live to the Supabase DB and re-verified: a real slip now sends successfully end-to-end (Playwright, `playwright/qa-verify-permission-slip-rls.js`).
- [x] **Policy Builder crashed the page on ~2/3 of generations** — `draft.relatedLegislation.join is not a function`. The AI's tool-call response isn't a hard type guarantee even with a forced schema; when `related_legislation`/`suggested_additions` came back as a string (or another shape) instead of an array, the client crashed rendering it, and a missing/blank `title` could also hit a not-null violation on save. Added `sanitizeRawPolicy()` in `lib/anthropic.ts` — coerces both fields to a clean string array and falls back to `"{category} Policy"` for a missing title — wired into both `generatePolicy()` and `regeneratePolicyFromReview()` so every caller gets the same safety net, plus a defensive `Array.isArray()` guard on the client as a second layer. Found and fixed during the 2026-08-18 QA follow-up.
- [x] **A missing/misconfigured `SUPABASE_SERVICE_ROLE_KEY` took down the whole app, not just AI routes** — `isRateLimited()` called `createAdminClient()` unguarded near the top of nearly every `/api/*` route handler; a synchronous throw from a missing key happened *before* the route's own try/catch, producing an opaque empty 500 in under 1.5s that the frontend misread as a generic network error. This was misdiagnosed as an Anthropic billing outage at least twice (2026-07-26, 2026-07-27) before the real cause was found 2026-08-18. The key itself is now set in both `.env.local` and Vercel production, but `isRateLimited()` is now also wrapped in a full try/catch so this specific failure mode can't recur and take the whole app down again — it fails open (request allowed, error logged) the same way an RPC-level error already did.
- [x] **PDF uploads silently broken in Import & Review, DOCX unaffected** — `pdf-parse` (via `pdfjs-dist`) locates its worker script relative to its own real `node_modules` path at runtime; Next's default Server Components bundling relocates the module and breaks that lookup (`Cannot find module '.next/.../pdf.worker.mjs'`). Fixed by excluding both packages from bundling via `serverExternalPackages` in `next.config.ts`. Found during the 2026-08-18 QA follow-up while re-testing AI-blocked features.
- [x] **Printable A3 program calendar could silently print blank** — entries with no `block_key` assigned yet (or one that no longer matches after a block was renamed/removed) matched none of the fixed block rows and were dropped from the printed calendar entirely, with no indication anything was missing. Added an "Other activities" fallback row that surfaces any unsorted entries per day, mirroring the same fallback already used on `/programs/[id]/today`. Found during the 2026-08-18 QA follow-up.

- [x] **Encrypt-at-rest for medical/compliance fields** — `children.additional_needs`, `child_health_plans.*` (triggers/signs_and_symptoms/emergency_steps/emergency_medication), and `staff_compliance.reference_number` (WWCC etc.) were plaintext in Supabase, protected only by RLS — same as every other table in the app (confirmed: no `centres`/`organisations` sensitive fields — WWCC, invoices — have any encryption either). New `lib/encryption.ts` does application-layer AES-256-GCM, key held only in server env (`FIELD_ENCRYPTION_KEY`), never in Supabase — a leaked service-role key or raw DB dump alone can no longer read these fields, both the key AND DB access are required. Production now encrypts these fields going forward; nothing was backfilled, so older rows stay plaintext until next edited/saved. **Not yet set for Preview/Development Vercel environments** — low priority since those fail open to plaintext too, but worth doing if preview deploys start being trusted with real data.

## Image generation (Pollinations) — outage resolved, but free tier is rate-limited not "down"
- **2026-08-05:** Pollinations.ai (the free, keyless image API `/api/generate-image` relies on for every printable sheet's picture) started returning HTTP 402 "Insufficient balance" for every model. Every picture-having sheet (activity sheet, drawing frame, card set, name colouring) couldn't produce a real picture.
- **2026-08-18:** The 402 outage is over — a single request now succeeds fine, no code change needed for that part. But repeat-testing same-session found it's **not fully healthy**: rapid/concurrent requests from the same IP now get HTTP 429 ("Queue full for IP... max: 1"). This isn't a depleting daily quota — nothing is "used up" — it's a live concurrency limit on the free **Anonymous** tier (per Pollinations' own docs: 1 request per 15s anonymous, vs 1 per 5s + no watermark on the free **Seed** tier, which just needs registering the app at auth.pollinations.ai — still $0, no payment). This explains why testing (regenerating after an imperfect result, or a card set's multiple images) trips errors: any burst of requests, from any single visitor's own IP, collides with itself. Real users will hit the exact same wall independently on their own connections — it isn't a shared pool that testing "uses up" for later, so pausing self-testing doesn't bank anything.
- **Next step (needs the user, free, ~5 min):** register the app's current live URL at auth.pollinations.ai to move off the Anonymous tier. Browsers already send an unauthenticated referrer header (`Referrer-Policy: strict-origin-when-cross-origin` in `vercel.json` still sends the origin cross-origin), so this may lift the limit with no code change at all once registered — confirm after signing up.
- **Code fix already applied (2026-08-18, this session):** `CardSetTemplate` in `WorksheetClient.tsx` now auto-retries a failed card image up to 2 times with backoff (6s/12s) before falling back to the manual "retry" button, so a transient 429 self-heals instead of needing a click. Single-image flow (`generateImage`) already has a manual "Generate" button as its retry path; not changed.
- Only worth paying for a faster Pollinations tier ("Flower") if the free Seed tier proves insufficient once registered — and even then it's a rate-limit speed upgrade, not a per-image credit cost, so "each imperfect generation costs more" doesn't really apply here the way a metered API would.
- **Fixed while investigating (commit pending):** two real app bugs, independent of the outage above —
  (a) `name_colouring` sheets never had an image option at all; wired to the same `image_subject` field the AI already sets for other templates (only when the educator's request implies a theme — plain name sheets stay text-only).
  (b) Every picture-having sheet silently showed a permanent blank box on ANY image failure (not just this outage) — the small preview thumbnail's error handler called `setImageUrl(null)`, wiping the shared image state out from under the full-size picture before it could show its own error. Now each shows its own "Image couldn't be generated" message instead.
  Verified with Playwright (`playwright/tests/name-colouring-image.spec.ts`) — with the real outage still in effect, the sheet now shows the clear error message instead of hanging in "Generating…" or going blank.
