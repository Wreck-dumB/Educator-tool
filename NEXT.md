## Parked: cross-tenant sharing ("Educator Exchange") vs. template library (2026-08-26)
A Copilot session was mid-conversation about a proposed cross-tenant sharing feature when it hit its credit limit — no code was written, purely analysis, worth keeping:
- [ ] **Don't call it "Wall"** — `/wall` (Community Wall) already exists as a single-service, parent-facing noticeboard. A cross-tenant sharing feature needs its own name (e.g. "Educator Exchange") to avoid confusion with the real live feature.
- [ ] **This would be the app's first cross-tenant feature.** Every table today is isolated per-service via `has_service_role()`. There's a documented precedent for why this is dangerous: migration 0055 fixed a token-redemption flow with an identity-binding gap that let someone join another centre's data via a leaked invite link (see [[project_sparkplay_security_audit]] in Claude's memory) — the bug wasn't in RLS, it was in a flow that punched a deliberate hole without fully verifying who was on the other end. Any sharing feature is exactly that kind of hole and needs its own narrow table + policy, never built by loosening existing access.
- [ ] **Low priority right now, on purpose:** with one centre currently live, there's no one to share with yet — real value once a second centre onboards, zero value today, and it's the riskiest piece to get right. Don't design the PII-scrubbing/moderation approach under time pressure; give it its own focused session once it's actually about to matter.
- **Recommended instead:** build a template library first — immediately useful, no new risk surface, doesn't touch cross-tenant boundaries. Revisit Educator Exchange when a second centre is close to onboarding.

## Recently fixed
- [x] **Name-trace "single line" font: overlapping letters + broken dot spacing** — found mid-session as pre-existing uncommitted work while fixing the print-blank-image bug below. Letter advance came from the font table's unreliable `width` field (understated real ink extent, e.g. "W"), causing overlap; fixed by measuring each glyph's own path. A dot-alignment attempt then broke dot sizing (percentage-of-stroke-length dashing made short strokes like an "i" stem nearly invisible and long diagonals nearly solid); fixed by sizing each stroke's dasharray off its real computed length instead. Verified visually via Playwright screenshots, multiple names, before/after. (commit `2eb79d5`) Deployed live.
- [x] **Permission Slips: infinite RLS recursion blocked every send** — `permission_slips` and `permission_slip_targets` (migration 0013) had circular RLS policies, each doing a raw `EXISTS` subquery against the other; Postgres has to re-evaluate each table's own policies while resolving a cross-table subquery, so A needed B evaluated, which needed A evaluated again. 100% reproducible (`42P17 infinite recursion detected in policy`) on every real send — found during the 2026-08-18 QA pass. Migration 0063 moves the cross-table reads into two `SECURITY DEFINER` helpers (`permission_slip_owner`, `permission_slip_sent_to_linked_child`), same established pattern as `has_service_role()`/`is_linked_parent()` elsewhere in this schema — a security-definer function's internal queries aren't subject to the caller's RLS re-evaluation of the *other* table, so neither policy re-enters the other's stack. Also closed a related, previously-latent gap surfaced while tracing this: `permission_slip_targets`/`_versions`/`_signatures` were still gated on the pre-0020 `educator_user_id = auth.uid()` check, which only the Director's own uid ever satisfies — 0020 widened `permission_slips` itself to let 2IC+ create slips on the service's behalf, but never updated these sibling tables, so a 2IC could pass the parent slip's INSERT check yet be blocked from inserting its version/targets rows. Rewritten to `has_service_role()` to match 0020's intended model. Applied live to the Supabase DB and re-verified: a real slip now sends successfully end-to-end (Playwright, `playwright/qa-verify-permission-slip-rls.js`).
- [x] **Policy Builder crashed the page on ~2/3 of generations** — `draft.relatedLegislation.join is not a function`. The AI's tool-call response isn't a hard type guarantee even with a forced schema; when `related_legislation`/`suggested_additions` came back as a string (or another shape) instead of an array, the client crashed rendering it, and a missing/blank `title` could also hit a not-null violation on save. Added `sanitizeRawPolicy()` in `lib/anthropic.ts` — coerces both fields to a clean string array and falls back to `"{category} Policy"` for a missing title — wired into both `generatePolicy()` and `regeneratePolicyFromReview()` so every caller gets the same safety net, plus a defensive `Array.isArray()` guard on the client as a second layer. Found and fixed during the 2026-08-18 QA follow-up.
